# Architecture

Nisaba is a monitoring platform for development-cooperation projects. It is a
**multi-tenant** system: every persisted object is scoped to an
`organization_id`, enforced by Cognito custom claims and Amplify `@auth` rules.

## Components

```
                ┌─────────────────────────────────────────────────────────────┐
                │              AWS Amplify backend (single deployment)        │
                │                                                             │
   web-app ─────┤  AppSync GraphQL (DynamoDB) ─ Cognito ─ S3 ─ Lambda(s)      │
   (Vue 3)      │                                                             │
                │  Lambdas:                                                   │
   mobile-app ──┤   • analyticsApp (Python) — analytics + XLSX export         │
   (Flutter)    │   • nisabaUserManagement — admin CRUD on users              │
                │   • authnisabaPreTokenGeneration — injects org_id claim     │
                │   • migrateSurveyStatus, createDefaultsForTesting, …        │
                └─────────────────────────────────────────────────────────────┘
```

- **One deployed environment** today: `release` (eu-central-1, AppSync app
  `d26pqqtndacxsh`, CFN stack `amplify-nisaba-release-21818`).
- Auth: Cognito user pool, with `custom:organization_id` written by the
  pre-token-generation Lambda and used as the owner field for all models.
- Migration scripts (in `backend/src/*.mjs`) and `analyticsApp` use IAM auth
  against AppSync; everything else uses Cognito Id-Token auth.

## Top-level layout

| Path           | Role                                                                                       |
| -------------- | ------------------------------------------------------------------------------------------ |
| `backend/`     | Source of truth for the Amplify backend (schema, Lambdas, auth, storage) + admin scripts.  |
| `web-app/`     | Vue 3 + Vite admin & analytics SPA. Hosted on Amplify Hosting (`amplify.yml`).             |
| `mobile-app/`  | Flutter field-data app for offline survey execution.                                       |
| `lib/`         | Cross-language shared definitions (S3 path constants, schema mirror, CI helpers).          |
| `scripts/`     | Legacy node admin tooling; mostly superseded by `backend/src/*.mjs`.                       |
| `.github/`     | GitHub Actions workflows for release-tag + deploy-to-prod.                                 |

`web-app/amplify/` and `mobile-app/amplify/` exist as **local copies** of the
Amplify project so the CLI can build/regenerate types for each frontend. The
canonical schema is the one in `backend/amplify/backend/api/apinisaba/schema.graphql`.
If you edit the schema, edit the canonical one and `amplify pull` (or copy) in
the consumer apps — they are not auto-synced.

## Web app (`web-app/`)

- **Stack:** Vue 3 + `<script setup>` + TypeScript, Vite, Pinia, Vue Router,
  vue-i18n, PrimeVue + Tailwind, Plotly for analytics charts.
- **Entry:** `src/main.ts` configures Amplify with a header provider that
  attaches the Cognito Id-Token to every GraphQL request.
- **State:** Pinia stores in `src/stores/` — most importantly
  `auth.ts` (login + role), `user.ts`, `projectConfigStore.ts` (the loaded
  org-wide config), `analytics.ts`.
- **Data access:** `aws-amplify`'s GraphQL client driven by generated
  types in `src/API.ts` and queries/mutations in `src/graphql/`. Helpers in
  `src/utils/` (`s3Paths.ts`, `newObjects.ts`, `objectCleaner.ts`, …).
- **Auth flow:** `AuthenticationState` enum in `stores/auth.ts` drives routing
  via `router/index.ts` navigation guards; role-based access uses
  `types/UserGroup.ts` with `minRole` route meta.

## Mobile app (`mobile-app/`)

- **Stack:** Flutter (Dart SDK ≥ 3.6), `flutter_bloc` for state, Amplify
  packages (`amplify_api`, `amplify_auth_cognito`, `amplify_storage_s3`),
  Hive + sembast for local persistence.
- **Custom sync layer (important):** instead of Amplify DataStore, the app
  uses a hand-rolled `SyncedDB` in
  `lib/backend/database/db_implementations/synced_db/` that composes a
  `LocalDB` (sembast/Hive) and a `GraphQLDB` (`graphql_db/`) and runs a
  `Synchronizer` plus a `DBQueue` for offline writes. See
  [design-decisions.md](design-decisions.md) for why.
- **Models:** Generated by the local `db_model_generator/` package (a Dart
  build_runner package) — do not edit `lib/models/*.dart` by hand. Regenerate
  via `flutter pub run build_runner build` (see [commands.md](commands.md)).
- **UI:** `lib/frontend/pages/` (login, main menu, survey, task form, …);
  `lib/frontend/components/` are the shared widgets.
- **BLoC providers:** `AuthRepository`, `UserRepository`,
  `LocalDataRepository`, `SessionCubit`, `SyncBloc`,
  `RequestPermissionsCubit` are wired in `main.dart`.

## Backend (`backend/`)

- **Amplify resources** under `backend/amplify/backend/`:
  - `api/apinisaba/schema.graphql` — canonical data model (~16 `@model` types).
  - `function/analyticsApp/` — Python 3 Lambda behind API Gateway, handlers in
    `src/handlers/`, services in `src/services/`. Endpoints exposed via the
    `proxy` path under `/getExecutedSurveyCountsForOrganization`,
    `/getAggregatedSurveyDataById`, `/getSurveyResultsAsXLSX`.
  - `function/authnisabaPreTokenGeneration/` — injects `custom:organization_id`.
  - `function/nisabaUserManagement/`, `AdminQueries8dc38185/` — user CRUD.
  - `auth/authnisaba/`, `auth/userPoolGroups/` — Cognito groups (`ADMIN`,
    `ANALYTICS`, …) feed `UserGroup.ts` in the web app.
  - `storage/nisabarelease/` — S3 bucket; path layout described in
    `migration_changes.md` and centralised for the frontends in
    `web-app/src/utils/s3Paths.ts` + `lib/utils/s3PathDefinitions/`.
- **Admin / migration scripts** in `backend/src/*.mjs` use IAM credentials via
  the AWS default credential chain. Always run with `--dry-run` first. See
  `backend/MIGRATION_IAM_SETUP.md` for required IAM permissions.

## S3 layout

All keys are prefixed with `organization/{organizationId}/`. Path helpers
(three runtime sources, currently aligned after the migration documented in
`backend/src/migrate-s3-paths.mjs`):

- Web: `web-app/src/utils/s3Paths.ts` (single source of truth for the SPA).
- Mobile: `mobile-app/lib/backend/storage/dataStorePaths.dart`.
- Lambda: `backend/amplify/backend/function/analyticsApp/src/queries/data_store_paths.py`.

`lib/utils/s3PathDefinitions/dataStorePaths.dart` (under top-level `lib/`)
is a **stale shared template** still showing pre-migration paths
(`appliedInterventionFiles/{id}/…`, `.mp3` audio). It is not loaded at
runtime — its header explicitly says it has to be copied into the consuming
app's `lib/` folder. Treat it as deletable; don't read it as authoritative.

Historical pre-migration state lives in `migration_changes.md` — useful
context but no longer describes today's code.

## Authorization model

Almost every model uses:
```graphql
@auth(rules: [
  {allow: owner, ownerField: "organization_id", identityClaim: "custom:organization_id"},
  {allow: private, provider: iam}
])
```

- The owner rule scopes records to the user's organization.
- The IAM rule is what lets admin/migration scripts and Lambdas operate
  cross-org with elevated AWS credentials.

## CI / deployment

- `.github/workflows/release.js.yml` — generates a release tag on push to `main`.
- `.github/workflows/prod.js.yml` — runs `lib/cicd/node/deploy/deploy.sh`
  (Amplify CLI deploy) gated by a label check.
- `web-app/amplify.yml` — Amplify Hosting build spec for the SPA.

There is no test pipeline today.
